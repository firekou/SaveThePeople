## 1. 終點與產品定位
服務鏈（不可偏離）：
被可信任的窗口接觸 → 說明需求 → 得知可能適用的資源 → 理解資格與缺漏 → 完成申請 → 追蹤補件與審查 → 實際取得幫助 → 持續更新與續辦。

北極星指標：**新增實際取得幫助的家庭數**（定義見 §7）。同時追蹤等待時間、服務工時與成本。

平台定位：
- 是「協助員＋社工＋資源維護者」的共同工作工具，加上給受助者的公開查詢與簡短問答入口。
- 不是核定機關，不做正式資格判定，不代替本人簽署，不假設有政府 API 或線上送件介接。
- 人工服務（電話、紙本、現場）是一級流程，不是例外流程；所有功能都必須能由協助員代為操作。

## 3. 角色定義
| 代碼 | 角色 | 說明 | 帳號 |
|---|---|---|---|
| R1 | 受助者（本人） | 家庭中主要尋求協助者；可為成年家長或照顧者 | 初篩免帳號；持續服務期可選用簡易身分確認（試點後） |

| R4 | 社工／專業複核窗口 | 複核初篩、處理裁量與例外、急迫需求、複雜家庭、品質抽查 | 內部帳號＋MFA；可為合作據點社工 |
| R5 | 資源維護與查核人員 | 來源登錄、條件結構化、查核、發布、變動監測 | 內部帳號＋MFA |

| R8（輔助） | 成果報告檢視者 | 負責人、資助方會議用；只看匿名彙總 | 內部帳號；無個案存取 |
| R9（輔助） | 獨立覆核者 | 檢查規則、資料與成果；唯讀抽樣，存取需案件層級授權並留稽核 | 內部帳號＋MFA |

規則：
- 一人可兼多角色，但「自己查核的資源版本」不得由自己發布；「自己承辦的案件成果」不得由自己作為品質抽查者驗收。
- R4 的專業判斷記錄在系統中，但正式責任仍依其所屬機構規範。

### 4.3 各角色的限制與例外（驗收依據）
| 角色 | 可做 | 明確不可做 |
|---|---|---|
| R1 本人 | 查看與更正自己的資料、撤回同意、回報取得（E1）、要求查閱存取紀錄 | 看到內部專業註記（`restricted_note`）、安全旗標；看到其他家庭資料 |
| R2 代理人 | 僅限 Consent.proxy 範圍與期間內查看／修改／聯絡／陪同送件 | 超出範圍、授權過期後的任何存取；撤回本人的同意（除非授權明列）；看安全旗標 |
| R3 協助員 | 責任人或備援案件的查看與修改、依同意分享轉介、登錄成果；以 VERIFY 範圍驗證**另一位 R3 負責**、非自己登錄、且被指派的單筆事件摘要（§4.5） | 非指派案件；驗證自己登錄或自己負責案件的取得事件；發布資源；匯出個案資料 |
| R4 社工 | 複核佇列與抽樣案件、成果驗證、更正（AP-19～23、RF-18、OC-08／09）、核發 REVIEW_SAMPLE | 複核自己承辦的案件；跨據點存取（除非同意書允許）；越過 AccessGrant 看非複核案件 |
| R5 資源維護 | 資源、來源、規則、查核；發布（發布人≠查核人） | 任何個案內容；發布自己查核的版本 |
| R6 提供機構 | 僅處理「轉介給自己」且同意有效的轉介：看 `shared_fields`、回覆受理狀態、容量與服務開始／完成確認 | 其他轉介、其他家庭、文件下載、跨機構資料；試點初期不設帳號，由 R3 代為登錄 |
| R7 管理者 | 帳號與角色、設定、稽核 metadata、保存與刪除作業（看不到內容）、BG 申請與核准 | 一般瀏覽個案內容（**無一般 V 權限，只能經 BG**）；自己申請並自己核准 BG；修改或刪除稽核事件 |
| R8 報告檢視者 | 匿名彙總報表與其匯出 | 下鑽到個案或家庭、匯出個案資料、查看 n<5 的格子 |
| R9 獨立覆核者 | 唯讀：公開與內部資源資料、規則與測試、稽核彙總；`REVIEW_SAMPLE` 授權下的去識別化抽樣案件；寫入獨立的覆核意見（ReviewNote，不改任何被覆核資料） | 修改任何資料；匯出個案資料；超出授權範圍或期限；看到識別資訊（除非另有 BG 等級的雙人核可與負責人書面同意，且限定用途 INDEPENDENT_REVIEW） |

### 4.4 BREAK_GLASS 與 REVIEW_SAMPLE
| 項目 | BREAK_GLASS（R7 或其他需例外存取者） | REVIEW_SAMPLE（R9） |
|---|---|---|
| 用途 | DATA_CORRECTION、DELETION_REQUEST、INCIDENT_INVESTIGATION、LEGAL_REQUEST | INDEPENDENT_REVIEW |
| 申請與核准 | 申請人與核准人為不同人（R7＋資料責任人或指定第二人），書面理由 | R4 或負責人核發，記錄抽樣規格與欄位範圍 |
| 範圍 | 指定案件與欄位，不得擴大 | 抽樣案件清單，預設去識別化（`case_code`、無聯絡方式、無自由文字、敏感值遮蔽） |
| 期限 | ≤4 小時 | ≤14 天 |
| 稽核 | 每次存取寫 AuditEvent（含 `access_grant_id`）；事後通知資料責任人；月度檢視 | 同左；覆核意見留於 ReviewNote |
| 匯出 | 不可（刪除或更正在系統內完成） | 不可 |

### 4.5 其他 R3 驗證成果事件（VERIFY 範圍）
- 對象：驗證人由 R4 或負責人**指派**的單筆 OutcomeEvent；驗證人必須≠登錄人、≠該案責任人與備援，且在系統中不是該案任何承辦。
- 可見內容：事件摘要（類型、日期、取得證據等級與描述）。**不含**家庭、成員、文件、聯絡方式、其他事實；VERIFY 不提供任何一般案件讀取，也不能列出未被指派的案件。
- 動作：只有 V 與 A（驗證）；不能 E。驗證後寫 AuditEvent（含驗證人與事件 id）。
- 矩陣是唯一依據：API（`GET /api/outcome-events/pending-verification`、`POST /api/outcome-events/{id}/verify`）、P7「待我驗證」與測試（T-50）都引用同一份 `permissions.json`；工具 `gen_permissions.py` 的政策檢查會在 VERIFY 被擴大或 API 授權超出矩陣時失敗（這是文件政策檢查，不是產品授權行為測試）。

### 4.6 分享、匯出與兼任規則
- 任何對外分享（轉介、提供機構、代理人）必須對應一筆有效 Consent 的用途與對象，系統在送出前檢查；分享內容限於 `shared_fields`。
- 匯出個案資料（CSV、列印）預設關閉；需 R4 核可並記錄用途；R7、R8、R9 不得匯出個案資料。列印行動清單給本人本身不屬於匯出，但會寫入 ActionPlan 交付紀錄。
- R8 與資助方溝通只用匿名彙總；不得提供名單、聯絡方式或可辨識案例。
- 一人可兼多角色，但「自己查核的資源版本」不得由自己發布；「自己承辦案件的成果」不得由自己驗證，也不得作為該案的品質抽查者；R9 不得同時是被覆核工作的作者。

## 5. 功能清單與分期
每項功能對應服務成果（O1～O7），沒有對應成果的功能不進入規劃。

成果代碼：
- O1 接觸：需要幫助的人經可信任管道進入服務。
- O2 知道：得知可能適用資源並理解條件與缺漏。
- O3 啟動：本人決定申請並備妥文件。
- O4 送達：完成送件或轉介並有收件證據。
- O5 不漏追：補件、審查與轉介回覆被追蹤到結果。
- O6 取得：實際取得幫助並被驗證。
- O7 持續：政策／家庭變動、續辦被處理。
- OQ 品質與成本：錯漏推薦、工時、成本可量測。

## 7. 成果報告定義（統計口徑）
所有報表排除 `is_synthetic = true` 的資料；示範環境與正式環境資料庫分離。口徑與參數版本化：每份報表是一筆 ReportRun，記錄 `metric_spec_version`、使用的參數（§7.6）、資料截止時間與資源目錄快照；參數或口徑改變時以新版本重算，並保留舊版本與差異說明，不覆寫。**本節的參數值多為暫行值**，哪些已成立、哪些待負責人決定見 §7.6。

### 7.1 計數單位與去重
- **家庭**：以 `Household.id` 計。同一家庭重複進線時，協助員在建案時以私有系統內的比對提示（`dedup_fingerprint`）確認後合併，保留合併 AuditEvent；不自動合併。無法確認者分開計並標記 `possible_duplicate`，報表另列。
- **申請件**：以 `Application.id` 計；唯一約束與重新申請、救濟、補充申請的建立規則見 [DATA_MODEL_AND_STATE_MACHINES.md](DATA_MODEL_AND_STATE_MACHINES.md) §2.13。`kind` 為 REAPPLY／APPEAL／SUPPLEMENTARY 的申請件另列，不與 ORIGINAL 混計轉換率。
- **資源項次**：同一家庭取得多項資源，家庭只計 1 戶，資源項次另計（每個 Outcome 一項）。
- 家庭若在觀察期內分戶或合併，以首次建案時的 `Household.id` 計，變動另列註記。

### 7.2 階段定義
| 階段 | 計入條件（家庭至少一件符合） | 必要證據 |
|---|---|---|
| 接觸 | 建立 ServiceCase，且有接觸管道紀錄 | 接觸紀錄 |
| 初篩完成 | 有效同意下完成至少 1 次 Assessment（狀態 EVALUATED 或 REVIEWED） | Assessment 紀錄 |
| 啟動申請 | Application 進入 PREPARING_DOCS 以後，且有本人／代理人確認 | 本人確認紀錄 |
| 送件／轉介 | Application 進入 SUBMITTED，或 Referral 進入 SENT 且有對方收件 | 收件憑據（收據、案號、Email 回覆、電話紀錄含對方姓名與時間） |
| 核准 | Application 進入 APPROVED；Referral 進入 ACCEPTED | **核准證據** A1～A3（見下） |
| **實際取得** | 有至少一筆**已驗證**的取得事件（見 §7.2.1），且 `Outcome.is_new_to_household = true` | **取得證據** E1～E3（見下）＋第二人驗證 |

**核准證據（Application.approval_evidence，只證明核准）**：A1 本人告知（須標記待確認）；A2 承辦或提供機構確認；A3 核定書或通知已查看（記錄類型、日期、查看人，不強制保存影本）。
**取得證據（OutcomeEvent.evidence_level，證明已實際取得）**：
- E1 本人或代理人口頭／書面確認（記錄日期、金額或服務內容概要）。
- E2 提供機構或承辦人確認已給付或已提供服務。
- E3 取得文件證據（物資簽收單、入帳通知已查看等；只記錄已查看，不強制保存影本）。
**核定書（A3）不能作為取得證據**；不要求銀行明細。報表同時呈現各等級數量。

「新增」：建案時記錄家庭目前已使用的資源（`baseline_resources`，含 `since`）；取得的資源若在建案前回溯期內（暫行 12 個月，§7.6）已在使用中，不計為新增，另列為「協助續辦」；`since` 未知者另列為「未確認是否新增」，不計入新增。

不得計為取得：合成示範、通知已發送、已送件、已核准但尚未給付或服務尚未開始、未經第二人驗證的取得事件、核定書本身。

#### 7.2.1 取得事件的計數方式（以 OutcomeEvent 為準，不以 Outcome 狀態為準）
可執行規格：`examples/ref_engine.py` 的 `count_outcomes` 與 `engine_cases.json` 的 `outcome_scenarios`（T-39～T-42）。
| 事件／情況 | 對「新增取得家庭」 | 對「資源項次」 | 說明 |
|---|---|---|---|
| FIRST_RECEIPT／FULL_RECEIPT／PARTIAL_RECEIPT（已驗證、未作廢、E1～E3） | 該家庭**首次**已驗證取得的日期落在觀察區間內 → 該區間計 1 戶；之後區間只列入累計 | 每個 Outcome 首次已驗證取得落在區間內 → 計 1 項 | 部分取得也算取得（標記 `partial`）；同一 Outcome 其後的完整取得不增加戶數或項次 |
| PERIOD_CONFIRMED（週期性給付或持續服務確認） | 不計 | 不計 | 另計「給付期數」；Outcome 轉 ONGOING 或 ENDED 不影響已計入的取得 |
| DUPLICATE_PAYMENT_NOTED（重複給付） | 不計 | 不計 | 通知 R4 評估是否須通報機構；不增加成果 |
| CORRECTION（更正，`voids_event_id`） | 作廢被更正事件；若該事件是家庭唯一已驗證取得，則家庭自該報表重算後移出 | 同左 | 報表以 `known_at`（資料截止）計算：更正發生在報表截止之後者，舊報表保持原樣，新報表以更正後結果重算，並於 ReportRun 記錄 `restatement_note` |
| 事件尚未驗證，或驗證人＝登錄人／案件責任人 | 不計，列為「待驗證」家庭數 | 不計 | 第二人必須是 R4 或另一位非責任人的 R3；驗證後才進入正式計數 |
| 核准但尚無取得事件（T-14） | 不計 | 不計 | 列為「核准待取得」 |
| `is_new_to_household=false` | 不計新增 | 不計 | 另列「協助續辦」 |
| 事件缺 `evidence_level` | — | — | 拒絕寫入（資料驗證錯誤），不靜默忽略 |

### 7.3 轉換率與觀察期間
- 每個轉換率必須寫明：分子、分母、觀察起訖日。例：「試點第 1～90 天完成初篩的 26 戶中，截至第 90 天有 11 戶實際取得（42%）」（數字僅為格式示例，非預測）。
- 主要報告點：試點第 90 天（來自 [EXECUTION_PLAN.md](../EXECUTION_PLAN.md) 的 90 天計畫）；追蹤報告點：第 180 天（暫行，待負責人決定，D-305，理由見 G-03）。
- **審查中**（SUBMITTED／UNDER_REVIEW／SUPPLEMENT_REQUESTED、Referral WAITLISTED）另列，不計成功也不計失敗。
- 撤回、失聯、不核准、額滿各自列數量與原因。

### 7.4 時間、工時與成本
| 指標 | 定義 |
|---|---|
| 首次接觸 → 行動清單 | ServiceCase.created_at 至首份 ActionPlan 交付（`delivered_at`）時間，中位數與 P90 |
| 啟動 → 送件 | 本人確認申請至 SUBMITTED |
| 送件 → 結果 | SUBMITTED 至 APPROVED／DENIED |

| 每戶成本 | （人力工時×費率＋系統月費分攤＋交通等直接支出）÷服務家庭數 |
| 每成功取得家庭成本 | 同上總額 ÷ 新增實際取得家庭數 |

### 7.5 品質
